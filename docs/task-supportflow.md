SupportFlow — мультиагентний асистент підтримки: план курсового проєкту
SupportFlow — це навчальна система підтримки покупця. Вона класифікує звернення, знаходить інформацію у внутрішній базі знань і через Silpo MCP, за потреби виконує вебпошук, а складні або критичні звернення передає оператору. Проєкт не є офіційним сервісом «Сільпо».
1. Мета і межі проєкту
Мета — реалізувати тему курсової «Система підтримки клієнтів» і додати практичну інтеграцію з Silpo MCP. Система має дати обґрунтовану відповідь із джерелами або чесно повідомити, що даних недостатньо, та створити звернення для оператора.
Система працює лише на читання: вона не оплачує замовлення, не змінює кошик і не виконує фінансових операцій. Це зменшує ризик помилок і спрощує захист персональних даних.
Приклади запитів
? Знайти безлактозне молоко та перевірити доступні варіанти отримання.
? Пояснити правила використання бонусів або сертифікатів на підставі бази знань і даних Silpo MCP.
? Запропонувати підтверджені альтернативи, якщо товар недоступний.
? Передати оператору критичне звернення або запит, для якого система не має достатніх даних.
2. Основні терміни
? MVP (Minimum Viable Product) — мінімальна працездатна версія проєкту, яку можна продемонструвати й протестувати.
? LLM (Large Language Model) — велика мовна модель, яка класифікує запити та формує відповіді.
? MCP (Model Context Protocol) — протокол, через який агент отримує доступ до зовнішніх інструментів і даних. У цьому проєкті використовується Silpo MCP.
? ACP (Agent Communication Protocol) — протокол обміну завданнями та результатами між локальним координатором і агентами. У MVP це внутрішній контракт викликів у межах одного процесу, а не окремий мережевий сервіс.
? RAG (Retrieval-Augmented Generation) — формування відповіді з попереднім пошуком релевантних фрагментів у базі знань.
? API (Application Programming Interface) — програмний інтерфейс, через який вебчастина та агенти обмінюються даними.
? UI (User Interface) — користувацький інтерфейс.
? OAuth (Open Authorization) — стандарт безпечної авторизації для доступу до Silpo MCP.
? JSON (JavaScript Object Notation) — текстовий формат для зберігання структурованих даних.
? Golden dataset — контрольний набір запитів із очікуваними результатами, маршрутами та викликами інструментів.
? End-to-end test — наскрізний тест повного маршруту запиту від введення користувачем до фінальної відповіді або ескалації.
3. Обов’язкові компоненти курсової
? Router Agent — класифікує звернення за категорією, терміновістю та мовою.
? Docs Agent — шукає відповідь у внутрішній базі знань за підходом RAG і, для доменних запитів, використовує Silpo MCP.
? Web Search Agent — шукає актуальну зовнішню інформацію через Tavily (основний провайдер) з fallback на DuckDuckGo, коли внутрішніх джерел недостатньо.
? Escalation Agent — формує структурований звіт, зберігає його у файл і надсилає реальне повідомлення в тестовий Telegram-канал.
? LangGraph StateGraph — керує станом, послідовністю агентів і умовними переходами.
? Pydantic — перевіряє структуру даних, які агенти передають один одному.
? Langfuse — трасує повний шлях запиту, зберігає версії системних інструкцій і запускає автоматичні оцінювання.
? DeepEval і pytest — запускають компонентні, інструментальні та наскрізні тести.

4. Архітектура системи
Схема взаємодії: вебінтерфейс ? локальний LangGraph Supervisor ? агенти через ACP ? інструменти й джерела даних.
LangGraph Supervisor — локальний координатор
? Зберігає стан поточного звернення.
? Викликає Router, Docs, Web Search та Escalation Agents через ACP. Кожен ACP-виклик передає ідентифікатор запиту, завдання, термін виконання та ідентифікатори трасування Langfuse; відповідь перевіряється відповідною Pydantic-моделлю.
? Порівнює впевненість відповіді з порогом і за потреби запускає ескалацію.
? Виконує умовні переходи, обмежує повторні спроби та обробляє помилки й перевищення часу очікування.
? Не виконує пошук самостійно і не дублює роботу агентів.
Ролі агентів
? Router Agent не має інструментів. Він повертає тільки структуровану класифікацію.
? Docs Agent використовує пошук у базі знань і дозволені інструменти Silpo MCP. Він повертає відповідь, джерела та оцінку впевненості від 0 до 1.
? Web Search Agent використовує Tavily, а за його недоступності — DuckDuckGo. Він не отримує персональні дані користувача й не підтверджує стан кошика, бонусів або замовлення.
? Escalation Agent створює зрозумілий для оператора звіт, записує його у файл і надсилає Telegram-сповіщення.
5. Джерела даних та інструменти
? Silpo MCP — основне джерело актуальних доменних даних. Перед реалізацією виконується tools/list — стандартний запит MCP, що повертає доступні інструменти та схеми їхніх аргументів.
? Внутрішня база знань містить 15–25 відповідей на часті запитання, 2–5 сторінок опису сервісів і 5–10 прикладів діалогів.
? Кожен документ у базі знань має джерело, дату отримання та версію правила.
? Вебпошук — Tavily як основний провайдер, DuckDuckGo як безключовий fallback — використовується лише для актуальної загальної інформації, якої немає у внутрішніх джерелах.
? Файлова система зберігає звіти про ескалації, а Telegram надсилає повідомлення в тестовий канал.
Silpo MCP є джерелом даних про товари та доступні сервіси. База знань є джерелом правил і довідкових матеріалів. Вебпошук не використовується як доказ персонального стану користувача.
6. Контракти даних
Обов’язкові моделі Pydantic
? ClassificationOutput: category — категорія запиту (Literal: product, general, critical); urgency — терміновість (Literal: low, medium, critical); language — мова.
? DocsResponse: answer — відповідь; sources — список джерел; confidence — впевненість від 0 до 1.
? WebSearchResponse: answer — відповідь; sources — список вебджерел; confidence — впевненість від 0 до 1.
? EscalationOutput: summary — короткий опис; category — категорія; customer_message — повідомлення користувачу; attempted_resolution — уже виконані спроби вирішення.
Стан LangGraph зберігає початковий запит, класифікацію, результати пошуку, відповідь, впевненість, помилки, ідентифікатори сесії та трасування Langfuse і наступну дію.
7. Послідовність роботи
1. Вхідний фільтр перевіряє мову, межі предметної області та наявність персональних або заборонених даних.
2. Supervisor через ACP викликає Router Agent.
3. Критичний запит одразу переходить до Escalation Agent.
4. Запит про продукт, правила або сервіс переходить до Docs Agent, який використовує базу знань і Silpo MCP.
5. Загальний запит, що потребує актуальної зовнішньої інформації, переходить до Web Search Agent.
6. Якщо впевненість нижча за встановлений поріг, джерела суперечливі або інструмент недоступний, викликається Escalation Agent.
7. Для успішного маршруту Supervisor формує коротку фінальну відповідь із джерелами.
8. Після завершення Langfuse зберігає повне дерево викликів і результати автоматичного оцінювання.
8. Організація коду і вебінтерфейс
Для коду використовується Clean Architecture. Це єдина архітектура організації програмних модулів у проєкті. Схема Supervisor–agents описує взаємодію компонентів, а не конкуруючу архітектуру коду.
Шари Clean Architecture
? Domain — Pydantic-моделі, стан LangGraph і правила маршрутизації, які не залежать від зовнішніх сервісів.
? Application — Supervisor і сценарії обробки звернень.
? Infrastructure — клієнти Silpo MCP, OpenRouter, Tavily, DuckDuckGo, Telegram, файлової системи та Langfuse.
? Interfaces — FastAPI та вебінтерфейс.
Вебчастина
? FastAPI надає API для запуску звернення та отримання результату; CORS відкрито лише для локального фронтенда.
? Вебінтерфейс — навмисно простий застосунок React 19 (збірка Vite): одна сторінка чату для роботи з агентом, яка надсилає звернення через REST і показує відповідь із джерелами.
? Модель OpenRouter для кожного агента, температура, максимальна кількість токенів, час очікування та поріг упевненості задаються у файлі config/models.yaml.
? Сторінка налаштувань у вебінтерфейсі — можливе розширення, якщо залишиться час після обов'язкового обсягу.
? Ключі доступу зберігаються на сервері у змінних середовища та не відображаються у вебінтерфейсі.
? Файли до 250 рядків є бажаними; модулі на 250–320 рядків допускаються, якщо зберігають одну відповідальність; більші файли логічно поділяються.
9. Langfuse та захист даних
Langfuse є єдиною платформою спостереження за роботою агентів. Кожен запуск має одне дерево: Supervisor ? agent ? model ? tool. Для кожного кроку зберігаються тривалість, помилка, використана модель, кількість токенів і вартість. Агенти продовжують отриману трасу, тому виклики моделей та інструментів залишаються в тому самому дереві.
? Системні інструкції всіх чотирьох агентів зберігаються та версіонуються в Langfuse Prompt Management.
? Langfuse автоматично оцінює нові траси за допомогою LLM-as-a-Judge — мовної моделі, яка виступає оцінювачем за визначеними критеріями.
? У Langfuse не записуються ключі доступу, OAuth-токени, повні адреси, телефони, email, платіжні дані або необроблені персональні дані.
? У демонстрації, базі знань і golden dataset використовуються синтетичні користувачі.
? Перед вебпошуком персональні дані видаляються. Якщо це неможливо без втрати змісту запиту, вебпошук не викликається.
? Доступ до Silpo MCP обмежується дозволеним списком операцій читання.
Практичне підключення Langfuse
Для трасування використовується Langfuse SDK, який працює на основі OpenTelemetry. Окремий OpenTelemetry Collector — служба збирання телеметрії — і додаткові модулі її передавання в MVP не розгортаються. LangChain і LangGraph трасуються через Langfuse CallbackHandler, а Silpo MCP, ACP, Telegram і File System — через власні Langfuse observations (окремі записи про виконані операції).
? CallbackHandler передається в налаштування кожного запуску graph.invoke, щоб вузли LangGraph, виклики моделей, стандартні інструменти та компоненти пошуку в базі знань потрапляли в одну трасу.
? Для Silpo MCP, ACP, Telegram, File System, очищення персональних даних і логіки Supervisor створюються окремі observations. У безпечних метаданих зберігаються назва агента й інструмента, категорія та терміновість від Router Agent, оцінка впевненості, ідентифікатор сесії, статус, тривалість, кількість повторів, тип помилки, модель і версія системної інструкції.
? Supervisor передає через ACP ідентифікатори трасування Langfuse, а агент продовжує отриману трасу. Окремі непов’язані траси для одного звернення вважаються помилкою.
? У Langfuse не передаються ключі доступу, OAuth-токени, повні персональні дані або необроблений вміст чутливих запитів. Ідентифікатори користувачів мають бути псевдонімізованими.
? У короткоживучих тестах і командних сценаріях перед завершенням процесу виконується примусове надсилання подій (flush) або коректне завершення клієнта (shutdown), щоб не втратити відкладені записи.
? Критерій готовності: один наскрізний запуск створює одну трасу з Supervisor, вибраним агентом, моделлю, інструментами, фінальною відповіддю та оцінками. Критичні помилки мають статус і пояснення, а непов’язані записи відсутні.
10. Тестування та автоматизоване оцінювання
Golden dataset
? 18 прикладів у JSON: 6 типових сценаріїв, 6 граничних випадків і 6 сценаріїв відмови.
? Кожен приклад містить поле input (запит), expected_output (очікуваний результат), очікуваний маршрут, дозволені й заборонені інструменти та ознаки персональних даних.
? Окремо покриваються недоступність Silpo MCP, помилка OAuth, перевищення часу очікування, недостатні докази, позадоменний запит і критична ескалація.
Компонентні тести
? Router Agent: щонайменше 10 класифікаційних запитів із відомими правильними категоріями.
? Docs Agent: відповідь має спиратися на базу знань або Silpo MCP і не містити вигаданих фактів. Запит поза базою знань має давати низьку впевненість і вести до ескалації.
? Web Search Agent: кожне твердження має підтримуватися поверненим вебджерелом.
? Escalation Agent: звіт має містити достатній контекст, опис уже виконаних кроків і зрозуміле повідомлення користувачу.
? Supervisor: перевіряються всі умовні маршрути, поріг упевненості та переходи до ескалації.
Перевірка правильності інструментів
? Router Agent не викликає інструменти.
? Docs Agent викликає Silpo MCP лише для запитів, де потрібні доменні дані.
? Web Search Agent викликає Tavily або DuckDuckGo лише для дозволених зовнішніх запитів.
? Escalation Agent створює файл і надсилає справжнє тестове Telegram-повідомлення.
Наскрізне оцінювання
? Повний golden dataset запускається командою deepeval test run tests/.
? Основні метрики від 0 до 1: Answer Relevancy — відповідність відповіді запиту; Groundedness — підтвердженість відповіді джерелами.
? Додаткові метрики: Route Correctness — правильність маршруту; Tool Correctness — правильність інструментів; Privacy Safety — відсутність витоку персональних даних.
? Власна метрика GEval (Generative Evaluation, генеративне оцінювання) Support Resolution Quality перевіряє, чи відповідь вирішує проблему, пояснює обмеження та пропонує правильний наступний крок.
? Початкові пороги встановлюються після першого повного запуску. Орієнтир: Answer Relevancy не нижче 0,70; Groundedness не нижче 0,75; Support Resolution Quality не нижче 0,70.
? Покриття тестами для доменної та прикладної логіки — не менше 80%; критичні маршрути й захист даних покриваються повністю.
11. Структура репозиторію і результати
? src/domain — моделі даних і правила.
? src/application — Supervisor і сценарії.
? src/infrastructure — інтеграції з моделями, Silpo MCP, пошуком, Telegram, файлами та Langfuse.
? src/interfaces — FastAPI; frontend — простий застосунок React 19 з власною збіркою.
? data/knowledge_base — база знань; evals/golden_dataset.json — контрольний набір; tests — усі тести.
? README містить опис запуску, схему архітектури, налаштування змінних середовища, відомі обмеження й команди тестування.
? Для захисту готуються панель Langfuse, звіт DeepEval, звіт про покриття тестами та коротке відео або жива демонстрація.
12. План реалізації
1. Перевірка вимог і доступу. Зберегти доступну копію project_support.md; виконати tools/list для Silpo MCP; перевірити OAuth, назви інструментів і схеми аргументів. Після цього скоригувати всі наступні етапи.
2. Каркас системи. Реалізувати Pydantic-моделі, стан LangGraph, Supervisor, Router Agent і ACP-виклики. Після компонентних тестів переглянути етапи інтеграції.
3. Дані та пошук. Додати базу знань, Docs Agent, Silpo MCP і Web Search Agent. Після тестів інструментів уточнити маршрути та поріг упевненості.
4. Ескалація й безпека. Додати Escalation Agent, файл, Telegram, очищення персональних даних і обробку помилок. Після тестування переглянути сценарії відмови.
5. Спостереження та оцінювання. Підключити Langfuse, DeepEval, golden dataset і метрики. За результатами першого повного запуску скоригувати системні інструкції, пороги та решту плану.
6. Вебінтерфейс і захист. Завершити сторінку чату, README, архітектурну схему та демонстрацію. Провести фінальну перевірку вимог і відомих обмежень.
