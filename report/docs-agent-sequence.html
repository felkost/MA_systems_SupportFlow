Docs Agent · one request

Docs Agent's own work — retrieve, translate, search, compose

run_docs_agent always reads the knowledge base first, then asks the chat model to extract and translate a Ukrainian search term before ever touching Silpo MCP — the catalogue is Ukrainian-language data, so an untranslated query would silently return nothing. Silpo MCP is skipped entirely when there's no product term to search, and any Silpo failure except an expired auth token degrades to an empty result rather than failing the request. There are two separate merges, easy to mistake for one: retrieved text is merged first, to build the prompt; retrieved source metadata is merged last, to overwrite whatever the model claims about where its answer came from.

How to read this diagram — actor by actor, step by step

In plain terms. Five "lanes": Docs A2A Server is where the request arrives from Supervisor's A2A call. run_docs_agent is the orchestrator doing all the work described here. Retriever searches the static knowledge base. Chat model is used twice — once to translate, once to compose the answer. Silpo MCP is the external retail catalogue, called only when there's an actual product to look up.

Order matters: the knowledge base is always searched first. Only after that does a small LLM call pull out the product/category the customer meant and translate it to Ukrainian — because Silpo's catalogue is Ukrainian-language data, and searching it in the customer's own language would just return nothing. If that translation came back empty (the message wasn't about a specific product), Silpo MCP is skipped entirely — not called with an empty query. If it came back non-empty, Silpo MCP is queried; most failures there are swallowed and treated as "no products found," except an expired login token, which is treated as a real problem and raised instead of hidden.

Whatever came back from the knowledge base and (maybe) Silpo MCP is combined into one block of text — that's merge #1 — and handed to the chat model a second time, this time to actually write the answer. Right before returning, run_docs_agent does a second, different merge — of source metadata, not text — overwriting whatever source list the model claimed with the sources it actually retrieved. The model doesn't get to invent where an answer came from.

Five lifelines

  • Docs A2A Server — the process boundary Supervisor's A2A call lands on; everything else here happens inside this one process.
  • run_docs_agent — the orchestrator function; owns the whole sequence below.
  • Retriever — the hybrid (vector + BM25) search over the static knowledge base.
  • Chat model — the LLM, used for two different jobs in this one request: extracting/translating a search term, then composing the final answer.
  • Silpo MCP — the real external retail-catalogue tool server.

Sequence, step by step

  1. Docs A2A Server → run_docs_agent: run_docs_agent(masked_query) — the already-masked customer message, handed over once the A2A call lands. Since decision #77, conversation_history rides along too — not a function argument from Supervisor's own code, but a new key in the A2A call's SendMessageRequest.metadata (unmasked here — Docs Agent carries no "no personal data" restriction the way Web Search does). See session-memory-sequence.html for where it originates.
  2. run_docs_agent → Retriever: invoke(masked_query) → ← kb_docs — unconditional: the knowledge base is searched on every single request, whether or not it later turns out to be product-related.
  3. run_docs_agent → Chat model: translate_fn(masked_query) → ← search_term_uk — a small, separate LLM call whose only job is to pull out the product/category term and translate it to Ukrainian. It can legitimately return an empty string, and often should (a general question has no product to search).
  4. OPT [search term is non-empty] — the whole Silpo MCP branch is skipped outright when the translation step returned nothing:
    • run_docs_agent → Silpo MCP: search_products(search_term_uk) → ← products | error.
    • Note: an expired-auth error is not swallowed — it propagates up loudly, since that needs a human to re-authenticate. Every other failure degrades silently to an empty product list.
  5. Self message (merge 1 of 2) — retrieved_block = kb_texts + mcp_texts — this is a different merge from the one at the end: it combines the retrieved text content from both sources into one block, because that text is what the next step needs as its prompt input. Nothing about citations happens here.
  6. run_docs_agent → Chat model: compose_fn(prompt) → ← DocsResponse — the second, different LLM call: writes the actual customer-facing answer from the merged text block above, plus (since decision #77) the session's prior turns filling supportflow/docs's {{conversation_history}} slot — see prompt-architecture.html for that prompt section. The model returns its own sources field too — but that value doesn't survive the next step.
  7. Self message (merge 2 of 2) — sources = kb_sources + mcp_sources — a separate merge of source metadata (not text), and it runs after compose_fn on purpose: it overwrites whatever sources the model just claimed with the sources run_docs_agent can prove it actually retrieved. There's nothing to overwrite until the model has answered, which is exactly why this step comes last, not first.
  8. run_docs_agent → Docs A2A Server: DocsAgentResult(response, context, tools_called) (accent arrow) — carries the answer, the raw retrieved text (for the faithfulness evaluator), and which Silpo MCP tool actually got called (empty if it was skipped or failed).

Two merges, easy to confuse — what each one is

Both self-messages say "merge," and both combine a knowledge-base result with a Silpo MCP result — but they merge two completely different things, at two different points in the sequence, for two different reasons:

  • Merge 1 — text, before compose_fn: kb_texts + mcp_texts → retrieved_block. This is raw retrieved content (FAQ answers, product names and prices) joined into one string, because it has to exist before the prompt can be built — the model needs something to read.
  • Merge 2 — metadata, after compose_fn: kb_sources + mcp_sources → answer.sources. This is citation metadata (where each fact came from), and it deliberately runs after the model has answered, because its whole purpose is to replace whatever the model itself claimed as its sources with the real ones. Doing this before the model call would make no sense — there'd be no model-claimed value yet to correct.

What metadata actually flows through this diagram

The two branches don't carry the same metadata shape — the knowledge base is a curated, versioned document set; Silpo MCP is a live catalogue with no such concept.

  • From the Retriever (knowledge base): every chunk's Document.metadata carries id, source, retrieved_at, version. Only three of those four become part of the final Source object handed to the customer — ref=source (e.g. internal_policy/returns_v3.md), retrieved_at, and version (e.g. "3.1"). id stays internal — it's how the retriever indexes the chunk, never something a customer needs to see.
  • From Silpo MCP: each product result carries at least name and price (used to build the readable mcp_texts line, e.g. "Молоко 2.5%: 42 грн"). Its Source is built differently: ref="Сільпо: " + name (the product's own name, not an opaque product id — an id would be unreadable in the chat UI's source list) and retrieved_at=fetched_at (the moment of this call). There is no version — Silpo's catalogue has no document-revision concept the way the curated knowledge base does, so that field is simply left at its default empty string.
The point of the connections: the chat model is called twice for two unrelated jobs (translate, then compose) — never one call doing both. Silpo MCP is reached only through a translated, Ukrainian, non-empty term, and its failures are triaged: routine unavailability degrades quietly, an expired credential does not. The two merge steps look similar but are not the same operation — one assembles the prompt's input (text, before the model runs), the other corrects the model's output (metadata, after it runs) — and mixing up their order would either starve the prompt of content or have nothing left to correct.
