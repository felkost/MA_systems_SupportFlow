Observability

What actually reaches Langfuse, and what you can see there

All three processes — Supervisor, Docs Agent, Web Search Agent — open their own Langfuse spans independently, but every one of them shares the same trace_id, seeded once at the start of a request and carried across every A2A hop in the message metadata. Every span passes through two independent PII barriers before it's ever stored.

How to read this diagram

In plain terms. Three separate programs are running — Supervisor, Docs Agent, Web Search Agent — each in its own OS process. Each one opens its own named "spans" (little timed records: "I did X, it took this long, here's what happened") and sends them toward Langfuse. Before Langfuse actually stores anything, every span passes through two checks: one decides whether this span is even worth keeping, the other scrubs any personal data out of it. What ends up stored is one single "trace" per customer request — even though three separate processes contributed to it — because they all agree on the same trace_id, passed along in the A2A messages between them.

The two gates every span passes through before storage

  • should_export_span — composed onto Langfuse's own default filter with or, never replacing it. This matters: Langfuse's default already drops spans with no gen_ai.* attribute; replacing it instead of extending it would silently lose that default coverage too. This project's own contribution is an exact-match set of span names (_OWN_SPAN_NAMES) — deliberately not a prefix match, because a prefix like "a2a." was tried and confirmed live to also match ~1400 of the A2A SDK's own internal instrumentation spans in one short smoke test, none of which this project asked to trace.
  • mask_otel_spans — a second, independent PII redaction, applied at the moment of actual export, reusing the same email/phone/card regex patterns as the input-side masking. It's independent on purpose: input masking happens once, early; this catches anything that slipped through or was generated downstream (a composed answer, a tool's raw response) right before it leaves the process for good.

What ends up visible in Langfuse, and what you can actually follow

  • One trace per customer request — not one per process. All spans from Supervisor, Docs Agent, and Web Search Agent nest under the same trace_id, because that id (and the calling span's id, as parent_span_id) is carried in the A2A message's own metadata across the network hop — not inferred, not reconstructed after the fact.
  • Per-generation cost and latency — every generation-type span (Router, Docs, Web Search, Escalation composing) carries token usage, which Langfuse turns into cost against its model price table, plus the span's own duration. Summed across a trace, this is the real answer to "how much did this one customer request cost."
  • Exact prompt version — every generation links the specific prompt version actually used, not just the prompt's name. Since the "production" label is mutable (someone can promote a new prompt version at any time), only the version pinned per-generation lets you attribute a later result to the prompt that was actually live when it ran.
  • Input/output text, already redacted — every generation's input/output fields hold the actual compiled prompt and the actual parsed model response, after both masking passes.
  • Session grouping and comparison tags — session_id lets you pull every request in one customer session together; tag_trace lets separate evaluation runs (a baseline before a fix, a candidate prompt vs. production) show up as distinct, filterable groups instead of one undifferentiated pool of traces.
The point of the connections: three independent OS processes each keep their own exporter, but nothing about this trace is assembled after the fact — the shared trace_id and the chain of parent_span_id values are carried forward at the moment of the A2A call itself, so Langfuse only ever has to group what already arrived correctly parented. The two gates run on every single span with no exceptions: what isn't named gets dropped, and what might carry personal data gets scrubbed, before either check ever gets a chance to be skipped.
