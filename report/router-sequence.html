Router's own work — one classification call

router_node calls run_router, which owns the retry policy: it retries the same call_router attempt once on a timeout or invalid model output, then gives up. If every attempt fails, it returns classification=None and the graph fails closed to Escalation — decide_route() is never reached.

How to read this diagram — actor by actor, step by step

In plain terms. Four "lanes" in the diagram: Supervisor starts the whole process (the graph's first node). RouterAgent is the manager of one classification request — it owns the retries. call_router is the one who actually performs a single attempt to reach the LLM. Chat model is the LLM itself, the one that classifies the customer's message.

Step by step: Supervisor tells RouterAgent "classify this text" and hands over the masked customer message. A loop then begins (it can run at most twice — one attempt, one retry, if the first failed): RouterAgent tells call_router "try once"; call_router asks the LLM "classify this"; the LLM either succeeds — returning category, urgency, and language — or fails (ran out of time, or answered in a shape that doesn't validate); call_router passes the outcome back to RouterAgent, either the finished classification or an error.

What happens next depends on that outcome: if it succeeded, RouterAgent stops right there and moves on, without waiting for a second attempt. If it failed, RouterAgent tries once more (that's the one retry). If the second attempt also fails, that's it — no more attempts, there simply is no classification.

RouterAgent then returns the result to Supervisor — either a real classification, or "nothing worked" (None). In that second case, Supervisor already knows: no classification means the case goes straight to a human (Escalation), rather than guessing a category.

The essence in one sentence: Router tries to classify the customer's message, gives itself one retry in case of an LLM hiccup, and if both attempts fail, it honestly says "I don't know" instead of inventing an answer.

Four lifelines

  • Supervisor — the graph node router_node, the first node every request hits.
  • RouterAgent — the run_router() function; it owns the retry policy, nothing else does.
  • call_router — one attempt, no opinion about retries: checks the deadline, fetches the versioned prompt, calls the model, validates the result, and either returns or raises.
  • Chat model — the LLM call itself, forced into ClassificationOutput's schema.

Sequence, step by step

  1. Supervisor → RouterAgent: run_router(masked_text) — router_node hands over the already-masked customer message plus request_id/session_id/trace_id; nothing about routing has happened yet.
  2. LOOP [attempt ≤ max_retries, stop on success] — everything below runs at most twice (max_retries=1 by default: one first try, one retry):
    • RouterAgent → call_router: call_router(envelope) — builds an AcpEnvelope for this one attempt, with its own deadline.
    • call_router → Chat model: invoke(prompt) — a structured-output call, forced to return a valid ClassificationOutput or fail.
    • Chat model → call_router: result | timeout | invalid — either a valid classification, or the call times out, or the model returns something that fails schema validation.
    • call_router → RouterAgent: (classification, version) | raise — on success, returns the classification and the resolved Langfuse prompt version; on failure, raises TimeoutError or RouterInvalidOutputError — call_router itself never retries, it just reports what happened.
  3. Stop condition — a success inside the loop returns immediately (the loop body's own try block returns), it never waits out the remaining attempts. A failure is caught, logged into errors, and the loop tries again — until attempt exceeds max_retries, at which point the loop exits on its own with no classification.
  4. RouterAgent → Supervisor: RouterResult(classification or None) (accent arrow) — the outcome, either way. classification=None means every attempt failed; the caller (router_node) must fail closed straight to Escalation without ever calling decide_route() — a classification that never validated cannot drive a routing decision.
The point of the connections: the retry policy lives in exactly one place — RouterAgent (run_router). call_router is deliberately dumb: one attempt, no retries, no fail-closed decision of its own — it only enforces the deadline and validates the shape of the answer. This keeps "how many times do we try" and "what do we do about it" from being duplicated or disagreeing between two modules.
