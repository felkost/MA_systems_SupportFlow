Web Search Agent's own work — search with fallback, then compose

run_web_search tries Tavily first — the task's own required primary provider — and only calls the free, keyless ddgs (DuckDuckGo) library if Tavily raises. Unlike Docs Agent, only one provider's results are ever used per request, never both merged, and there is exactly one chat-model call, not two — there's no language to translate, since a general web search isn't restricted to a Ukrainian-only catalogue.

How to read this diagram — actor by actor, step by step

In plain terms. Five "lanes": Web Search A2A is where Supervisor's A2A call arrives. run_web_search is the orchestrator. Tavily is tried first. DuckDuckGo is tried only if Tavily fails. Chat model is called exactly once, just to write the answer — there's no translation step here like Docs Agent has, because a general web search isn't tied to one language.

Only one provider's results are ever used — never both. Tavily goes first because the task itself requires it as the primary provider; DuckDuckGo (via the free ddgs library, no API key needed) is the fallback specifically because it costs nothing to keep available, so the whole agent doesn't go dark just because a Tavily key is missing or Tavily is having an outage. If both fail, that's treated as a real problem — a tool-unavailable error that triggers escalation, not a silent empty answer.

Five lifelines

  • Web Search A2A — the process boundary Supervisor's A2A call lands on.
  • run_web_search — the orchestrator function; owns the fallback logic and the one compose call.
  • Tavily — the primary provider, a paid API requiring tavily_api_key.
  • DuckDuckGo — the fallback provider, reached through the ddgs library, free and keyless.
  • Chat model — the LLM, called once, to compose the final answer from whichever provider actually responded.

Sequence, step by step

  1. Web Search A2A → run_web_search: run_web_search(masked_query) — the already-masked customer message.
  2. ALT [Tavily succeeds] / [else — Tavily raised, try DuckDuckGo] — a genuine two-region branch, not two independent optional steps:
    • Region 1: run_web_search → Tavily: search(query, max_results=5) → ← up to 5 results, tagged provider="tavily".
    • Region 2 (only reached if Tavily raised any exception): run_web_search → DuckDuckGo: text(query, max_results=5) → ← up to 5 results, tagged provider="duckduckgo".
    • Note: if DuckDuckGo also raises, both attempts have now failed — that propagates as SearchUnavailableError, the task's own "tool unavailable" escalation trigger, not an empty result.
  3. Self message: retrieved_block = title + url + content, per result — whichever provider's results came back get normalized into one text block for the prompt. Both providers' raw responses are shaped differently (Tavily's own JSON vs. ddgs's own dict) but are normalized into the same provider-agnostic SearchResult shape before this point, so this step doesn't need to know which provider it came from.
  4. run_web_search → Chat model: compose_fn(prompt) → ← WebSearchResponse — the one and only LLM call in this whole sequence. It writes the answer and proposes its own sources — but only one field of those survives unedited.
  5. Self message: sources[i].retrieved_at = fetched_at (ref unchanged) — narrower than Docs Agent's equivalent step: this only patches the fetch timestamp on each source the model already produced; it does not replace the source list wholesale. The model's own ref/URL is trusted here, since it's directly quoting a URL it was just given, not inventing a document citation.
  6. run_web_search → Web Search A2A: WebSearchAgentResult(response, context, tools_called) (accent arrow) — tools_called is exactly one entry, ["tavily"] or ["duckduckgo"] — never both, since only one provider ever actually ran.

This is a genuinely different pattern from Docs Agent's knowledge-base + Silpo MCP branch: there, both sources are always combined when both are available. Here, the two providers are mutually exclusive — a strict "try A, else try B" fallback, never "merge A and B."

What data moves through this diagram, and what constrains it

  • Input constraint: masked_query must already be PII-masked before it reaches run_web_search — the function itself "has no opinion on masking," it only searches with whatever text it's handed.
  • Result-count constraint: both providers are called with max_results=5, hard-coded — never more than 5 results per provider, per request.
  • Shape constraint: every result, regardless of provider, is forced into SearchResult(title: str, url: str, content: str) — a fixed, provider-agnostic schema.
  • Provider tag constraint: SearchOutcome.provider is a closed Literal["tavily", "duckduckgo"] — no third value is possible, and it's set by search() itself, not guessed afterward from the data.
  • Timestamp constraint: retrieved_at is never trusted from the model — it's overwritten with this call's own fetched_at, so a source's claimed freshness always reflects when this agent actually fetched it, not when the LLM assumed it did.
The point of the connections: this is a fallback branch, not a merge branch — Tavily and DuckDuckGo are alternatives, never combined, unlike Docs Agent's knowledge-base-plus-Silpo-MCP pattern. The chat model is called exactly once, because there's nothing to translate first. And only the timestamp gets corrected after the model answers — the model's own source references are trusted here in a way Docs Agent's never are, because a web search source is a URL the model was just handed, not a citation it had to invent.
