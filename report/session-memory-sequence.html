Session memory · two turns, one checkpointer

How one turn's answer becomes the next turn's context

Session memory is not a node in the graph — it is an InMemorySaver checkpointer wrapped around every graph.invoke call, keyed by session_id as LangGraph's own thread_id. This diagram shows the one thing that is easy to get wrong about it: what a checkpointed thread actually does to a `TypedDict` field with no reducer versus one that has one — traced across two real turns in the same session.

How to read this diagram — the one thing to take away

In plain terms. Session memory is not a feature the graph "does" — it is a property of how graph.invoke is called. Every call passes the same four lifelines: the Browser sends one message, Supervisor starts one graph run, the LangGraph runtime (the compiled graph plus its InMemorySaver) owns the checkpoint, and whichever Terminal node actually resolves the case (Docs, Web Search, or Escalation) is the only place a new turn gets written.

Turn 1 in the same session finds no saved checkpoint, so it behaves exactly like a stateless request always did — empty history in, one new turn out, and a checkpoint is saved for the first time. Turn 2, using the same session_id, is where the mechanism actually does something: the runtime restores Turn 1's saved state before running anything, and the fresh empty seed build_initial_state always sends does not erase it — because conversation_history has its own reducer, not because LangGraph "remembers" by default.

The essence in one sentence: a checkpointed thread does not reset a field on every call — it merges the new call's value into whatever is already saved, through that field's own reducer, and only a field annotated with one behaves that way; everything else is simply overwritten, fresh, every turn.

Four lifelines

  • Browser — one tab, one session_id for as long as the customer keeps typing in it.
  • Supervisor — handle_request(); builds a fresh SupportFlowState every single call and passes session_id as the graph's configurable.thread_id.
  • LangGraph runtime — the compiled graph plus the module-level InMemorySaver it was compiled with (graph_nodes.py); this is the only place that actually knows a prior turn exists.
  • Terminal node — docs_node, web_search_node, or escalate_node; whichever one sets next_action to a resolving value is the one that appends a turn. router_node never does.

Why this needed its own diagram

  1. A `TypedDict` field with no reducer is not "session state" just because a checkpointer is attached. classification, docs_response, confidence and most of SupportFlowState are overwritten by each turn's fresh build_initial_state output — the checkpointer's merge only matters for the two fields that actually carry a reducer, conversation_history and errors.
  2. errors needed a bespoke reducer for the opposite reason conversation_history needed one. conversation_history wants to keep what a plain empty seed would otherwise leave alone. errors wanted the opposite: a live probe found operator.add making a checkpointed thread's error list grow forever across turns, since an empty-list seed merges to existing + [] == existing, never to []. _errors_reducer's RESET_ERRORS_MARKER is how build_initial_state tells the reducer "this is a new turn, actually clear it" — confirmed by a direct live probe against the installed checkpointer.
  3. Escalation reads history but never writes a prompt with it. It still appends a turn on resolution (so a later Docs/Web Search turn in the same session can reference "what I already told you"), but its own prompt has no {{conversation_history}} slot — it summarises the current case for a human operator, not a conversation.
The point of the connections: the checkpointer sits entirely outside the graph's own node logic — no node calls it, no node knows it exists. It intercepts exactly two moments, both drawn as notes on the runtime's own lifeline: restoring saved state before the merge at the start of graph.invoke, and saving the merged result after every super-step completes. Everything else in this diagram — Router deciding a route, Docs querying Silpo, Web Search calling Tavily/DuckDuckGo, Escalation writing a report — is unchanged by session memory existing at all; see router-sequence.html, docs-agent-sequence.html, web-search-agent-sequence.html, and escalation-sequence.html for those. In-memory only: a Backend restart drops every session's checkpoint, same ceiling as escalation_agent.py's own _session_store.
