Quality panel · backend

Where every number in the quality panel comes from

Three separate flows share one endpoint family. Recording is free and happens on every answered request. Reading is free and happens on page load, after each answer, and on the refresh button. Scoring costs money, runs only on cases never scored before, and executes in a separate interpreter — DeepEval brings its own OpenTelemetry instrumentation, and the API process already owns a TracerProvider configured for Langfuse, so loading both into one process would split a single chat request's trace in two.

What the backend actually computes

judge_stats.summarize() is the only place a statistic is produced, and it never calls a model. Everything it reports is arithmetic over numbers that already exist: the mean, the sample standard deviation, a 95% percentile bootstrap interval from src/domain/statistics.py, and the count of cases the metric applies to. The interval uses a fixed seed, so the same stored data always yields the same published interval.

Why the tag filter is not optional

Offline test-script runs never count toward this metric — only genuine answers to real users do. Enforcing that took a filter, because Langfuse itself does not separate the two: measured against the real project account, 138 of 160 scores under this evaluator's name were left there by offline test scripts, not live chat, and only one was a real live answer.

Without the filter, "the most recent 20 scores" would, with near certainty, have averaged offline test traffic — including a prompt that was tried and then rejected — and reported it under the caption "live system quality". live_quality() reads only scores carrying the currently configured experiment tag, which offline scripts never write, and reports unavailable rather than guessing when no tag is configured.

Why scoring is a subprocess and not a function call

The API process owns a TracerProvider configured for Langfuse. DeepEval attaches its own OpenTelemetry instrumentation to the global provider, and two instrumentors on one provider is exactly what splits a single chat request into two disconnected traces. A separate interpreter keeps that boundary intact, at the cost of one process spawn per button press. The batch is capped per call so one HTTP request cannot run unbounded; whatever is left over is reported as pending and picked up next time.

The one number the backend refuses to compute: a difference between the live Langfuse block and either DeepEval block. They are different rubrics on different inputs — the Langfuse judge receives the whole compiled agent prompt as its "customer message" and a Pydantic repr as its "agent response", while DeepEval receives the clean question and answer. Only the two DeepEval blocks share an instrument, and only they may be read against each other.
