Escalation's own work — compose, mask, confirm, write, send

escalate_node calls run_escalation_agent. It composes a report with one LLM call, masks PII in the output itself (a deterministic filter, not just a prompt instruction), then blocks on a human's yes/no before anything leaves the process — unless bypass_hitl is set, the automated-run escape hatch used by the golden-dataset gate. After confirmation it hashes the customer's masked message and checks an in-memory, session-scoped set of hashes already escalated this session — a repeat of the same message is deduplicated (no write, no send). The file write always happens after that; the Telegram send is a second, independent gate on top of it.

How to read this diagram — actor by actor, step by step

Four lifelines

  • Supervisor — the graph node escalate_node that triggers all of this.
  • EscalationAgent — the run_escalation_agent() function, the orchestrator of the whole scenario.
  • Chat model — the one LLM call that composes the report text.
  • Operator — a human at the terminal (blocking on stdin input()) — and, drawn separately on the right, Sinks — the report file plus Telegram.

Sequence, step by step

  1. Supervisor → EscalationAgent: run_escalation_agent(context) — escalate_node has already assembled an EscalationContext (the masked message, the classification, any errors, and whatever Docs/Web Search answer was produced before escalating) and hands it over.
  2. EscalationAgent → Chat model: compose_fn(prompt) → ← EscalationOutput — one LLM call composes a structured report: summary, category, customer_message, attempted_resolution.
  3. Self-loop: mask_pii(output) — EscalationAgent runs the result through a deterministic PII regex filter itself, with no external call. The prompt instruction alone is not trusted — this is the real control.
  4. OPT [not bypass_hitl] → Operator: confirm_fn(output) → ← y / N — a blocking CLI prompt: "Write report and send to Telegram? [y/N]". The whole step is skipped when bypass_hitl=True (automated runs, e.g. the golden-dataset gate).
    • Note: on N, the function returns right here — nothing further happens.
  5. Self-loop: sha256(masked_text) in seen_hashes? — only reached once confirmed (or bypassed): hashes the customer's masked input and checks it against the set this session has already escalated.
    • Note: if the hash was already seen this session, this is also an early return (dedup) — no write, no send.
  6. EscalationAgent → Sinks: write_fn(report) — the report file is always written once execution reaches this point (confirmed, and not a duplicate).
  7. OPT [allow_real_send, channel set, quota not capped] → Sinks: send_fn(telegram text) — a second, independent gate on top of the file write: even with a report on disk, a real Telegram message only goes out if allow_real_send is set, a chat_id is configured, and the per-session/per-process send cap has not been reached.
  8. EscalationAgent → Supervisor: EscalationAgentResult(written, sent) (accent arrow) — the final result reports whether the file was actually written and whether Telegram was actually sent, as two independent booleans — either step could have stopped earlier on its own.
The point of the connections: this is not one continuous flow but three sequential gates, each able to stop execution early — human confirmation → duplicate check → real-send quota. The file and Telegram are two distinct destinations (Sinks), and the file is always written first, independently of whether the Telegram message goes out.
