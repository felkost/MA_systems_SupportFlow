What the measured numbers say — and what each one is allowed to say

Two judges, five metrics, three populations. Only one pair of columns in this whole report may be compared with each other; the rest describe separate things that happen to be scored on the same 0–1 scale.

Measured 2026-08-28 against the live system. Live figures move as the demo is used — the panel in the chat page is the current version; this page is the reading of one snapshot.

The bracketed number is how many of that population's cases the metric applies to. It is below the total whenever the metric needs something a case does not have — faithfulness grades an answer against retrieved sources, and an escalation has none. Reported rather than levelled: forcing every metric onto every case would produce numbers about nothing.

Caution against the obvious reading. Support Resolution Quality of 0.600 live versus 0.672 on the dataset looks like real evidence that live traffic is harder. It is not: the bootstrap interval around that difference is [−0.099, +0.327], comfortably spanning zero. At these sample sizes "no difference detected" and "the samples are too small to detect one" are indistinguishable, and only more traffic separates them.

3 · What the numbers say about each part of the system

The generation model — strong

Faithfulness 1.000 and Answer Relevancy 1.000 on live traffic mean that when an agent does answer from sources, it does not invent facts and does not drift off topic. That is the model plus its prompt doing their job. The dataset scores slightly lower (0.935) because it deliberately contains harder cases.

The agent system — this is the weak link

Support Resolution Quality sits near 0.6 in both populations. That rubric asks whether the response resolves the problem, is honest about its own limits, and proposes a concrete next step. So the system tells the truth but frequently does not carry the case to a resolution — an orchestration and completeness problem, not a hallucination one. Route Correctness 0.889 belongs to the same family: two of eighteen cases went down the wrong branch.

The golden dataset — representative, but small

No metric shows a detectable difference between the dataset and live traffic, which is evidence that the dataset is not detached from reality. The coverage gap is by design rather than an omission: Answer Relevancy and Faithfulness apply to 9 of 18 cases because half the dataset is escalation and rejection paths, where there is no sourced answer to grade. The set is built as 6 typical, 6 edge, 6 failure cases.

4 · What each metric means — per judge

Two metrics can share a word and still measure differently. This section is the reference for reading any single number above.

LangfuseJudge inside Langfuse — one holistic call per answer

  • supportflow-answer-relevance — asks one model for a single 0–1 rating of how well a Docs or Web Search answer addresses the customer's message. Runs on the *_agent.compose observation, skipping any at level=ERROR. Reads the whole compiled agent prompt as its "customer message" and a Pydantic repr as its "agent response", which depresses its absolute level — its spread is trustworthy, its absolute value is not.
  • supportflow-escalation-quality — a separate rubric for handovers, because an escalation cannot score well on "does this answer the customer" by construction. Asks whether the response names why it could not be resolved automatically, states what was already attempted, and tells the customer what happens next.

DeepEvalOffline metrics — same model, different algorithms

  • Answer Relevancy — splits the answer into individual statements, judges each one relevant or not to the question, and reports the share that were relevant. Because it is a ratio over a handful of statements, it clusters at its ceiling.
  • Faithfulness — extracts the answer's claims and checks each against the retrieved sources; the score is the share supported. Requires sources, so it applies only to Docs and Web Search answers.
  • Support Resolution Quality (GEval) — the project's own rubric with three explicit steps: does it resolve the problem or explain why not, is it honest about its limits, does it propose a concrete next step. Applies to any case with a customer-facing answer, escalations included — "a human will follow up" is a valid next step.

DeterministicNot judged by a model at all

  • Privacy Safety — re-runs the project's own personal-data detector over the answer; 1 if clean, 0 if anything leaked. The most reliable number in this report, because no model opinion is involved. Its limit is its pattern list: emails, phone numbers, card numbers. A free-text address or an API token would pass.
  • Route Correctness — compares the branch actually taken against the branch the dataset expected. Live traffic has no expected branch, so this exists only on the golden dataset; deriving "expected" from what happened would score 1.0 by construction.
  • Tool Correctness — a list comparison of tools called against tools expected, on the Docs route only. Golden dataset only, for the same reason.

5 · Three caveats without which the numbers read wrong

  1. Answer Relevancy 1.000 with σ = 0.000 is not proof of excellence. A metric that returns exactly 1.0 on all seven cases is saturated: it cannot separate good from excellent, so it is useless here as a tool for finding problems. Treat it as a floor check ("nothing was wildly off topic"), not as a grade.
  2. Privacy Safety 1.000 across all 30 measured cases is the strongest evidence in this report, precisely because it is deterministic. It is also the narrowest: it proves the absence of known patterns, not the absence of leaked personal data in general.
  3. The two judges differ by a third on "relevance" (0.745 versus 1.000) — not a contradiction, two ways of counting. The informative part is which one does work: the holistic score separates cases (σ = 0.27); the statement ratio does not (σ = 0.00).
The one conclusion this data supports with confidence: the system does not fabricate and does not leak personal data, but in roughly a third of cases it fails to carry the request through to a resolution — and that holds equally for live traffic and for the golden dataset. Everything else here is either not yet distinguishable from noise, or a property of the measuring instrument rather than of the system.

Neither judge has ever been validated against human labels — no agreement statistic exists for either. The intervals above cover sampling uncertainty only; the judges' own repeat-run noise has never been measured, so the true uncertainty is wider than shown.
